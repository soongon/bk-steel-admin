## 3. v2 원칙

1. **행 = 다음 행동 하나.** 이름·전화가 있는 행은 전화 탭, 주소뿐인 행은 방문 탭. 두 유형을 한 리스트에 섞지 않고 버튼 세트도 다르게 둔다.
2. **처분될 때만 사라지고, 상태는 저장하지 않는다.** 오늘/대기/완료는 sales_log(기록·다음 행동일)·dismissed_at(제외) 두 곳에서 파생한다(linked_partner_id는 라벨용일 뿐 상태가 아니다). 수집기는 사람 컬럼을 절대 덮지 않는다. "오늘 0건"이 정상 상태. 창은 탭당 하나이며 시드/운영 구분을 두지 않는다.
3. **컷은 비공사만, 분류는 라벨, 보정은 제외 사유로.** 등급·점수·추정톤을 두지 않는다. 제목 키워드(strict v2)는 ▸RC 라벨과 비철근 공종 컷에만 쓰고(단일 판정자 라벨 = [추정]), 사용자의 [제외] 사유 분포가 2주차 필터 보정의 유일한 입력이다.
4. **가설은 화면보다 먼저 검증한다.** 전화 탭의 80%(A규칙)는 수요 신호가 아니라 '경주에서 활동 중인 토건사'라는 가설이다. 데이터는 이미 있으므로 D0에 전화를 걸기 시작하고, 화면은 판정 뒤에 짓는다.

## 8. DB 변경 최소안 — `0069_radar_v2.sql`

(레포 최신이 0068_audit_masters.sql이므로 0069 [확인]. 0060은 quote_line_ton_metric으로 이미 존재.) 신규 테이블 0 · 컬럼 6 · 인덱스 4 · RPC 1 · 트리거 0 · RLS 변경 0.

```sql
ALTER TABLE construction_project
  ADD COLUMN IF NOT EXISTS dismissed_at     TIMESTAMPTZ,
  ADD COLUMN IF NOT EXISTS dismiss_reason   TEXT,
  ADD COLUMN IF NOT EXISTS stage_changed_at TIMESTAMPTZ,            -- 단계(허가/착공/낙찰…)가 DB에 반영된 시각. 수집기가 §7 사전조회로 채움
  ADD COLUMN IF NOT EXISTS awardee_bizno    TEXT GENERATED ALWAYS AS
    (NULLIF(regexp_replace(coalesce(raw->>'bidwinnrBizno',''), '[^0-9]', '', 'g'), '')) STORED;
UPDATE construction_project SET stage_changed_at = GREATEST(created_at, stage_date::timestamptz)
  WHERE stage_changed_at IS NULL;                                   -- 1회 백필(근사, §7)
ALTER TABLE sales_log
  ADD COLUMN IF NOT EXISTS project_id    UUID REFERENCES construction_project(id),
  ADD COLUMN IF NOT EXISTS contact_phone TEXT;                      -- 현장·통화에서 확보한 번호(0016에 phone 컬럼 없음)

CREATE INDEX IF NOT EXISTS idx_cproj_v2_phone ON construction_project (stage_date DESC)
  WHERE deleted_at IS NULL AND dismissed_at IS NULL AND stage = 'awarded';
CREATE INDEX IF NOT EXISTS idx_cproj_v2_visit ON construction_project (region, stage, stage_changed_at DESC)
  WHERE deleted_at IS NULL AND dismissed_at IS NULL AND source = 'building_permit';
CREATE INDEX IF NOT EXISTS idx_cproj_awardee_bizno ON construction_project (awardee_bizno) WHERE awardee_bizno IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_sales_log_project ON sales_log (project_id) WHERE project_id IS NOT NULL AND deleted_at IS NULL;

UPDATE construction_project SET deleted_at = now() WHERE source = 'notice' AND deleted_at IS NULL;
NOTIFY pgrst, 'reload schema';
```

## 12. 리스크·미확인 가정

- **'소형 관급 낙찰 = 철근 수요'는 가설이다.** 거래처 8곳 중 현장이 기록된 5곳의 매출은 낙찰 공사가 아닌 다른 현장이었고 3곳은 현장 미기록이라 판단 불가 [추정 overlap]; 낙찰일↔매출일 근접 사례(정안 7/20↔7/15·7/27, 한맥 8/12↔9/22)는 증거 약함. 전화 탭 A행은 '활동 중 토건사 명부'로만 표기하고 2주 판정(견적 요청 수 + "낙찰 공사에 납품했는가" 보조 질문)으로 유지/축소를 정한다.
- **방문 탭의 '누구'는 표지판 가정 [추측].** 직영 소형 주택·빈 현장이면 헛걸음. '현장 없음' 제외 비율을 2주 후 측정(제외 사유에 별도 코드를 둔 이유).
- **건축HUB 지연 = API 0~60일(중앙값 2~3주) + 발행 주기 월 1회.** 착공 행은 D+36 이후에나 보이므로 기초 철근이 끝난 뒤일 수 있다. 허가 행 선점과 '기록 뒤 착공이면 오늘' 재부상으로 완화할 뿐 지연 자체는 못 줄인다. 주 2회 동기화도 발행 주기가 월 1회라 효과 없음 [확인 final].
- **stage_changed_at 백필은 근사.** day-1 값은 GREATEST(created_at, stage_date)라 허가로 들어와 착공으로 바뀐 행의 창이 실제보다 짧을 수 있다. 2회 동기화 뒤부터 정확.
- **낙찰 전환 시각 미측정.** 공고로 먼저 들어온 69%의 낙찰 반영 지연은 컬럼이 없어 잴 수 없다(낙찰 시점 생성 행만 p90 2일 [확인]). strict의 p50 4·p90 25일은 초기 적재가 섞인 값 [추정]. RADAR_NARA_DAYS=30이 보험.
- **루프 미가동 위험.** 전력 sales_log 1건/4개월. 담당·시간을 §9에 박았고, 1주차 끝에 주당 처분 10건 미만이면 필터가 아니라 UX를 고친다.
- **연락 채널 법적 리스크 [검증관 제시, 법률 자문 아님].** 정보통신망법 §50은 전자적 전송매체(문자·MMS·이메일)로 영리 광고성 정보를 보내려면 사전 동의를 요구하고, 예외는 거래관계 또는 '육성으로 수집 출처를 고지한 전화권유'뿐(과태료 상한 3,000만원 안내). 사람이 직접 거는 콜은 출처 고지로 가능하지만 레이더 번호로 견적서·명세서 MMS를 먼저 보내면 위반 소지 — 이 시스템에는 이미 MMS 발송 기능이 있어 실수하기 쉽다. 대응: 행에 문자 버튼 없음, MMS는 '견적 요청' 기록 뒤에만(가드), 통화 첫 문장 고정, 거절은 bizno 단위 영구 숨김, docs에 수집 출처·목적·보관 범위 기재. 조문 확인은 별도.
- **전화 마스킹은 산발적**(4%, 48/1,112; 월 2~15건; 발주처와 무관 — 농어촌공사 경주지사 29건 중 6, 울주군 128건 중 5 [확인 verify-plan]). 창 안 영향 계정 1. 전국건설업체정보 API로 보완 시도하되 채움률은 승인 후 실측 전엔 모른다.
