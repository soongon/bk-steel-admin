## 1. 한 줄 결론

매입 업무의 행 단위를 **매입문의(`purchase_inquiry`, 신규 테이블 1개)** 로 두고, 문의 1 : 견적 N : 매입 N 을 FK 두 개(`purchase_quote.inquiry_id`·`purchase.inquiry_id`)로 묶은 뒤, `/[book]/purchase-quotes` 를 **"오늘 매입 할 일" 보드**(오늘·대기·완료 칩 3개가 유일한 필터, 카드마다 **주 버튼 1 + [▾] 1**, 상세 페이지 없음)로 바꾼다. **상태는 저장하지 않는다** — 단계는 SQL 뷰 `vw_purchase_pipeline` 한 줄에서 순수함수 `derivePurchaseStage()` 가 파생하고, 저장되는 전이는 `closed_at` 뿐이다. 접수는 폰 60초(필수 = '판매자 또는 어디' 하나), 그 뒤 견적·계근·매입·결제는 **기존 화면으로 점프하되 prefill 로 재타이핑 0**(prefill 모드에서는 고정 칸을 접어 입력 칸만 노출). 인바운드 소스는 전화·방문·소개 + **홈페이지 문의**(`/[book]/inquiries` 상세의 [매입 접수] 1탭이 카드를 만든다, §6.4) 로 하나의 보드에 모인다. 종결·매입 생성처럼 여러 행을 바꾸거나 조건 검사가 필요한 전이만 DB 함수(종결 가드·책 정합·거래처 필수·DB 채번)로 둔다. 마이그레이션은 **PR 단위로 3개**: **0097**(PR-1: 문의 테이블·링크 FK·뷰·종결/재개 RPC·견적 RPC 보강·백필) / **0098**(PR-3: 매입 측 컬럼·계근 CHECK·DB 채번·`create_purchase_with_lines` 재정의 + 회귀 SQL 같은 PR) / **0099**(PR-4: `purchase_quote.inquiry_id NOT NULL`). 0078 은 비워 둔다(v1.1 문서가 예약한 번호 — 머리말). **PR-1(접수 + 오늘 보드, 1.5~2일)만 먼저 내보내 사장이 1주 써본 뒤** 수거·계근·종결을 붙인다.

## 3. 원칙

1. **카드 한 장 = 문의 한 건 = 주 버튼 하나.** 카드 액션바는 **주 버튼 1 + [▾] 1, 예외 없음**. 보류·종결·재견적·일정 변경·안내 문자·거래처 등록·수정·삭제는 전부 [▾] 메뉴. 사장이 보는 것은 "오늘 N건" 과 카드마다 큰 버튼 하나. 폰에서 보는 매입 화면은 보드 하나다(상세 페이지·칸반 없음).
2. **상태를 저장하지 않는다.** 단계는 `vw_purchase_pipeline` 한 행(문의 + 견적 집계 + 매입 집계)에서 `derivePurchaseStage()` 가 파생. 저장하는 전이는 `closed_at`(+`close_reason`) 뿐. 견적·매입이 soft-delete 되면 카드는 자동으로 이전 단계로 돌아간다 — 단, **매입에 쓰인 견적·견적/매입이 붙은 문의는 삭제를 거부**한다(§4.2, 파생이 가리키는 행이 사라지지 않게).
3. **들어온 카드는 종결될 때만 나간다.** 견적 0건인 문의는 **보류를 누르기 전까지 '오늘' 칩에 남는다**(기본 다음 연락일 +7일 같은 것 없음). 다만 오늘 칩 안의 **정렬은 단계 우선**(계근·등록 → 결제 연체 → 결제 → 견적/답 대기 → 종결 제안)이라 묵은 문의가 당장 할 일 위에 올라오지 않고, `STALE_DAYS`(기본 7)를 넘긴 견적 0건 문의는 오늘 칩 맨 아래 '오래된 문의 n건' 접힘 묶음으로 내려간다. "오늘 0건" 이 정상.
4. **기존 화면으로 점프, 새 폼은 접수 하나.** 견적은 `PurchaseQuoteDialog`, 매입은 `PurchaseFormDialog`(kg·EA 모두), 결제는 `PayDialog` — prefill·역링크만 더한다. **prefill 모드에서는 고정 칸(책·판매자·현장·자료성 등)을 1줄 요약으로 접고 입력 칸만 노출**한다(견적: 품목 칩 + 단가 1칸 / 매입: 계근 kg·공제 kg·결제예정일 칩). 세금계산서 수취는 보드 단계가 아니라 매입 상세 패널의 일(§8).
5. **견적은 단가표, 매입은 계근표.** 총액이 처음 생기는 곳은 매입 폼의 `정산kg × 원/kg`. 계근 원값(계근·공제)은 숫자 컬럼에 남긴다.
6. **거래처 마스터는 매입 시점에 확정, 단 '없으면 만든다' 가 아니라 '명시적으로 등록한다'**(절대 룰 3). 문의·견적은 자유 텍스트. 매입 등록은 `partner_id` 필수(RPC RAISE). 등록은 1탭 `[이 이름으로 거래처 등록]`(정규화 이름 + 전화번호 중복 검사) — 자유 텍스트 자동 승격(`resolvePartnerId`) 은 매입문의 경로에서 쓰지 않는다.
7. **책·자료성은 접수 때 정한다.** bk 는 사업자 판매자만(DB CHECK), b 는 무자료만 — 폼 잠금 + RPC RAISE + CHECK 3중. 견적·매입이 붙은 뒤 문의 책은 못 바꾼다(트리거).
8. **여러 행을 바꾸거나 조건을 검사하는 전이는 DB 함수에서.** 종결(문의 + 견적 done, 결제·계산서 가드), 매입 생성(책 정합·거래처·채번·견적 FOR UPDATE). 한 행 두 컬럼 갱신(수거 일정·보류)은 앱 UPDATE + `closed_at IS NULL` 가드 + audit.
9. **매출·레이더·메시지 provider 코드는 건드리지 않는다.** `quote*`·`radar*`·`lib/message/*`·`pay_purchase_with_payment` 변경 0.
10. **단계적 검증.** 가설 위에 5일짜리를 한 번에 짓지 않는다 — PR-1(접수·보드) → 1주 운영 → PR-2/3.

보조 전이(어느 열린 단계에서나, [▾] 메뉴):
- **[보류 ▾]** = `next_action_on` 지정 → 대기. 팝오버 **칩 4개: +3일 / +1주 / +2주 / 날짜 직접**(칩 선택, 기본 선택 없음 — 결제예정일 칩과 같은 UX).
- **[종결 ▾]**(매입 0건일 때만 노출) = 사유 3개 중 선택 `안 팜·단가 불일치`·`연락 불가`·`기타` → 완료. RPC: 매입 ≥1 이면 거부("매입이 있는 문의는 [종결] 으로"). 매입 ≥1 인 카드의 **[종결]** 은 사유 선택 없이 '매입 완료' 고정 — 사유는 총 **4개**.
- **[재견적]** = 마지막 견적 복제(새 doc_no, quote_date 오늘, valid_until +7일, 같은 inquiry_id).
- **[계근 후 매입 등록]** = **어느 열린 단계에서나 가능, 수거 확정은 선택**. 견적 없이 바로 트럭이 온 경우(5월 매입 5건 전부 당일 입고 [확인 `docs/reference-data/2.매입.csv`]) 1·2단계 ▾ 에서 바로 등록하면 재정의 RPC 가 `pickup_on = COALESCE(pickup_on, 매입.delivered_on)` 으로 수거일을 채운다(§5.1 8-a).
- **[이 매입인가요? 연결]** = 미연결 매입 제안(§4.4).
- **[삭제]** = `deletePurchaseInquiry(id)`: `EXISTS(purchase_quote WHERE inquiry_id=id AND deleted_at IS NULL) OR EXISTS(purchase WHERE inquiry_id=id AND deleted_at IS NULL)` 이면 **거부**("견적·매입이 있는 문의는 [종결 ▾] 로 닫으세요"). 0건일 때만 `deleted_at` UPDATE(`closed_at IS NULL` 가드 불필요). DB 에서도 같은 조건을 트리거 `purchase_inquiry_book_guard`(`BEFORE UPDATE OF book, deleted_at`) 가 RAISE 한다(§5.1 (3)). 삭제 가드가 없으면 견적 상세의 '문의 ←' 링크가 삭제된 문의를 가리키고, 그 매입은 `inquiry_id IS NOT NULL` 이라 §4.4 후보에서도 빠져 어느 카드에도 안 보인다.

**누가**: 사장(owner) 1인 운영 전제. staff 도 문의·견적·매입 INSERT 는 가능하나 **partner INSERT 는 owner/manager 전용**(`0019:266-293` [확인]) 이라 `[이 이름으로 거래처 등록]` 은 staff 에서 "권한이 없습니다" 가 뜬다 — 접수 폼·수거 팝오버에 그 안내를 적는다. **site INSERT 도 owner/manager 전용**(`0031_site.sql:55-56` [확인]) — staff 가 새 `site_name` 으로 등록하면 현장 마스터는 만들어지지 않고 `site_name` 텍스트만 저장된다(기존 수동 폼과 같은 동작, §13).

### 4.2 상태 전이 — 파생 규칙(`lib/purchase-pipeline.ts derivePurchaseStage()` (신규), 보드·아침 요약 공용 순수함수)

```
입력: vw_purchase_pipeline 1행 (문의 + 견적 집계 + 매입 집계) + today(kstToday)
반환: { stage, chip(today|waiting|done), dueOn, dueReason, badges[] }
closed_at IS NOT NULL ────────────────────────────────────────▶ done      완료 (90일 노출, [다시 열기])
quote_count = 0 ∧ pickup_on IS NULL ∧ purchase_count = 0 ──────▶ inquiry   오늘 (dueOn = next_action_on ?? received_on, dueReason '접수')
                                                                           today − received_on > STALE_DAYS(7) 면 '오래된 문의' 접힘 묶음
quote_count ≥ 1 ∧ pickup_on IS NULL ∧ purchase_count = 0 ──────▶ quoted    오늘 if (next_action_on ?? latest_sent_on+2 ?? today) ≤ today (dueReason '견적 발송 +2일')
overdue_count > 0 ─────────────────────────────────────────────▶ paying    오늘·연체(빨강)   ← scheduled/weighing 보다 먼저: 1차 트럭 연체가 2차 수거 일정 뒤에 숨지 않게
pickup_on > today ─────────────────────────────────────────────▶ scheduled 대기 (D-n, dueReason '수거일'); unpaid_count > 0 면 '미결제 n건' 배지 + 보조 [결제]
pickup_on ≤ today ∧ purchases_since_pickup = 0 ────────────────▶ weighing  오늘 (D+n 지남 = 빨강); unpaid_count > 0 면 '미결제 n건' 배지 + 보조 [결제]
unpaid_count > 0 ──────────────────────────────────────────────▶ paying    오늘 if (min_payment_due_on ?? last_delivered_on) ≤ today (dueReason '결제예정일')
그 외(매입 ≥1, 전부 결제) ─────────────────────────────────────▶ closable  오늘; last_paid_on + 14 < today 면 배지 '종결 제안 · n일 경과'(묶음 아님)
우선순위: 위에서 아래로 첫 매치. 오늘 칩 정렬 = 단계 우선(weighing → paying 연체 → paying → quoted/inquiry → closable) → 그 안에서 dueOn 오래된 순.
```

- `purchases_since_pickup` = **마지막 [수거 확정]/[추가 수거] 시각(`pickup_set_at`) 이후 `created_at` 인 매입 수**(뷰 컬럼). `ordered_on ≥ pickup_on` 기준이면 2차 트럭을 수거일 전날 미리 등록했을 때 '계근·등록' 이 영구히 오늘에 남으므로 쓰지 않는다. 매입 등록 시 `pickup_on` 은 그대로 두고, 등록된 매입이 그 시각 이후면 자동으로 4 → 5 로 넘어간다. [추가 수거] 는 `pickup_on`·`pickup_set_at` 을 새로 덮어쓴다. 견적 없이 1·2단계 ▾ 에서 바로 등록한 매입은 RPC 가 `pickup_on` 을 채운다(§5.1 8-a).
- `dueOn`·`dueReason` 은 보드 카드(대기 칩 1줄 "복귀 10/22 · 견적 발송 +2일")와 아침 요약이 같은 값을 쓴다 — 복귀 규칙이 단계마다 달라(received_on / sent_on+2 / next_action_on / pickup_on / payment_due_on ?? delivered_on / last_paid_on+14) 사장이 "왜 대기에 있고 언제 돌아오는지" 를 추론할 필요가 없게 항상 표기한다.
- 견적 status(draft/sent/done/expired)·매입 status(ordered/in_stock/…)는 **기존 그대로**. `done` 라벨만 '종결'. `expired` 자동 전이 없음(기한 경과 칩). `invoice_pending_count` 는 뷰에 남기되 **단계 파생에 쓰지 않는다**(카드 배지 '계산서 n건 미수취' 용).
- **soft-delete 후 정합**: 파생이므로 견적·매입을 지우면 카드가 이전 단계로 **조용히** 돌아간다. 삭제 토스트 문구는 `derivePurchaseStage(row − 그 견적/매입)` 로 **계산해서** 찍는다(매입이 1건이라도 있으면 견적을 지워도 '견적' 이 아니라 paying/closable 이므로 고정 문구는 틀린다). 가드 2개: **`deletePurchaseQuote`** 는 `EXISTS(purchase WHERE source_purchase_quote_id = id AND deleted_at IS NULL)` 이면 거부("매입에 쓰인 견적은 삭제할 수 없습니다" — 8-c 의 수정 거부가 삭제→[재견적] 으로 우회되고 뷰 `lq` 가 deleted 를 빼서 카드의 '최신 견적 단가' 가 조용히 바뀌는 것을 막는다, `purchase-quotes/actions.ts:197-` 수정) / **`deletePurchaseInquiry`** 는 §4.1 [삭제] 규칙. `soft_delete_purchase` 는 무변경.

### 4.4 "등록은 했는데 카드와 연결 안 됨" — 미연결 매입 제안 (세 안 공통 결함)

사장이 매입 메뉴에서 바로 등록하면(`inquiry_id NULL`) 카드가 **'견적/답 대기' 또는 '계근·등록'** 단계에 남는다(`pickup_on` 이 NULL 이면 파생은 quoted/inquiry 이지 weighing 이 아니다). 보드 로드 시 다음 휴리스틱으로 **카드에 "이 매입인가요? [연결]"** 을 띄운다:
- 기준일 = `COALESCE(pickup_on, latest_sent_on, received_on)`. 후보 = `purchase.inquiry_id IS NULL ∧ deleted_at IS NULL ∧ book = 문의.book ∧ delivered_on(또는 ordered_on) ≥ 기준일 − 1 ∧ ≤ 기준일 + 7` 이고, `partner_id = 문의.partner_id` 이거나 `normalizePartnerName(partner.name) = normalizePartnerName(문의.seller_name)`. (`pickup_on` 기준만 쓰면 수거 확정 없이 등록한 짧은 흐름에서 후보 조건이 항상 거짓이라 [연결] 수단이 없다.)
- [연결] = 앱 UPDATE `purchase.inquiry_id` (+ `source_purchase_quote_id` 는 최신 sent 견적이 있으면 제안). 책 불일치는 트리거 `purchase_inquiry_link_guard`(§5.1 (3)) 가 막는다. 매입 폼의 `?inquiry=` 프리필 경로와 동일한 결과.
- 뷰에는 넣지 않고 보드 서버 컴포넌트가 **quoted·weighing 두 단계** 카드에 한해 1쿼리로 조회(열린 문의 수 × 후보가 작다).

```sql
--    0097 시점엔 purchase.inquiry_id 가 없으므로 매입 집계는 0 으로 두고, 0098 에서 CREATE OR REPLACE 로 아래 본문으로 교체한다.
--    계산서 수취는 종결 조건이 아니다(§4.1) — 결제만 검사.
CREATE OR REPLACE FUNCTION purchase_inquiry_close(p_id uuid, p_reason text) RETURNS void
LANGUAGE plpgsql SECURITY INVOKER SET search_path = public AS $$
DECLARE v_cnt int; v_unpaid int; v_rows int;
BEGIN
  IF p_reason NOT IN ('매입 완료','안 팜·단가 불일치','연락 불가','기타') THEN RAISE EXCEPTION 'invalid reason %', p_reason; END IF;
  PERFORM 1 FROM purchase_inquiry WHERE id = p_id AND deleted_at IS NULL AND closed_at IS NULL FOR UPDATE;   -- 8-a 와 직렬화(COUNT~UPDATE 사이 매입 INSERT 방지)
  IF NOT FOUND THEN RAISE EXCEPTION '권한이 없거나 이미 종결된 문의입니다'; END IF;
  SELECT COUNT(*), COUNT(*) FILTER (WHERE paid_on IS NULL)
    INTO v_cnt, v_unpaid FROM purchase WHERE inquiry_id = p_id AND deleted_at IS NULL;   -- [0097] 에서는 v_cnt := 0; v_unpaid := 0;
  IF p_reason = '매입 완료' THEN
    IF v_cnt = 0  THEN RAISE EXCEPTION '매입이 없는 문의는 "매입 완료" 로 종결할 수 없습니다 — 다른 사유를 고르세요'; END IF;
    IF v_unpaid>0 THEN RAISE EXCEPTION '미결제 매입 %건 — 결제 후 종결', v_unpaid; END IF;
  ELSIF v_cnt > 0 THEN
    RAISE EXCEPTION '매입이 %건 있는 문의는 "매입 완료" 로 종결하세요', v_cnt;   -- done/lost 집계가 섞이지 않게
  END IF;
  UPDATE purchase_inquiry SET closed_at = NOW(), close_reason = p_reason, next_action_on = NULL, updated_by = auth.uid()
   WHERE id = p_id AND deleted_at IS NULL AND closed_at IS NULL;
  GET DIAGNOSTICS v_rows = ROW_COUNT; IF v_rows = 0 THEN RAISE EXCEPTION '권한이 없거나 이미 종결된 문의입니다'; END IF;
  UPDATE purchase_quote SET status = 'done', done_on = kst_today(), updated_by = auth.uid()
   WHERE inquiry_id = p_id AND deleted_at IS NULL AND status IN ('draft','sent');
END $$;
CREATE OR REPLACE FUNCTION purchase_inquiry_reopen(p_id uuid) RETURNS void
LANGUAGE plpgsql SECURITY INVOKER SET search_path = public AS $$
DECLARE v_rows int;
BEGIN
  UPDATE purchase_inquiry SET closed_at = NULL, close_reason = NULL, updated_by = auth.uid()
   WHERE id = p_id AND deleted_at IS NULL AND closed_at IS NOT NULL;
  GET DIAGNOSTICS v_rows = ROW_COUNT; IF v_rows = 0 THEN RAISE EXCEPTION '권한이 없거나 열려 있는 문의입니다'; END IF;
  -- 견적 done 은 되돌리지 않는다(새 단가는 [재견적]). 매입은 그대로.
END $$;
GRANT EXECUTE ON FUNCTION purchase_inquiry_close(uuid,text), purchase_inquiry_reopen(uuid) TO authenticated;

-- 11) [0097 → 0098 교체] 보드·아침 요약의 단일 데이터원 — security_invoker(호출자 RLS). 단계는 앱 순수함수가 계산(뷰는 집계만).
--     0097 에서는 purchase.inquiry_id 가 없으므로 pur CTE 없이 매입 집계 컬럼(purchase_count~purchases_since_pickup)을 0/NULL 상수로 두고,
--     0098 에서 CREATE OR REPLACE VIEW 로 아래 본문(pur CTE 포함)으로 교체한다. 컬럼 목록·순서는 두 버전이 같다(앱 타입 PipelineRow 1개).
CREATE OR REPLACE VIEW vw_purchase_pipeline WITH (security_invoker = true) AS
WITH lq AS (   -- 최신 견적 1건
  SELECT DISTINCT ON (inquiry_id) inquiry_id, id AS latest_quote_id, doc_no AS latest_quote_doc_no, status AS latest_quote_status,
         sent_on AS latest_sent_on, valid_until AS latest_valid_until, is_documented AS latest_is_documented
  FROM purchase_quote WHERE deleted_at IS NULL AND inquiry_id IS NOT NULL ORDER BY inquiry_id, quote_date DESC, created_at DESC
), qp AS (     -- 최신 견적 단가 범위
  SELECT l.purchase_quote_id, MIN(l.price_per_kg_krw) AS price_lo, MAX(l.price_per_kg_krw) AS price_hi
  FROM purchase_quote_line l WHERE l.deleted_at IS NULL GROUP BY l.purchase_quote_id
), qc AS (
  SELECT inquiry_id, COUNT(*) AS quote_count FROM purchase_quote WHERE deleted_at IS NULL AND inquiry_id IS NOT NULL GROUP BY inquiry_id
), pur AS (
  SELECT p.inquiry_id,
         COUNT(*)                                                                 AS purchase_count,
         COUNT(*) FILTER (WHERE p.paid_on IS NULL)                                AS unpaid_count,
         MIN(p.payment_due_on) FILTER (WHERE p.paid_on IS NULL)                   AS min_payment_due_on,
         COUNT(*) FILTER (WHERE p.paid_on IS NULL AND p.payment_due_on < CURRENT_DATE) AS overdue_count,
         COUNT(*) FILTER (WHERE p.is_documented AND p.tax_doc_type <> 'none' AND p.tax_invoice_received_on IS NULL) AS invoice_pending_count,  -- 배지용, 단계 파생엔 안 씀
         COALESCE(SUM(p.total_krw),0)                                             AS purchase_total_krw,
         COALESCE(SUM(p.total_krw) FILTER (WHERE p.paid_on IS NULL),0)            AS unpaid_krw,
         COALESCE(SUM(pl.kg),0)                                                   AS settled_kg,
         MAX(p.delivered_on)                                                      AS last_delivered_on,
         MAX(p.paid_on)                                                           AS last_paid_on,          -- 종결 제안 14일 기준
         COUNT(*) FILTER (WHERE i.pickup_set_at IS NOT NULL AND p.created_at >= i.pickup_set_at) AS purchases_since_pickup   -- §4.2
  FROM purchase p JOIN purchase_inquiry i ON i.id = p.inquiry_id
  LEFT JOIN (SELECT purchase_id, SUM(actual_weight_kg) AS kg FROM purchase_line WHERE deleted_at IS NULL AND acquired_unit='kg' GROUP BY purchase_id) pl ON pl.purchase_id = p.id
  WHERE p.deleted_at IS NULL GROUP BY p.inquiry_id
)
SELECT i.*, p.name AS partner_name, p.phone AS partner_phone,
       COALESCE(qc.quote_count,0) AS quote_count, lq.latest_quote_id, lq.latest_quote_doc_no, lq.latest_quote_status, lq.latest_sent_on,
       lq.latest_valid_until, lq.latest_is_documented, qp.price_lo, qp.price_hi,
       COALESCE(pur.purchase_count,0) AS purchase_count, COALESCE(pur.unpaid_count,0) AS unpaid_count, pur.min_payment_due_on,
       COALESCE(pur.overdue_count,0) AS overdue_count, COALESCE(pur.invoice_pending_count,0) AS invoice_pending_count,
       COALESCE(pur.purchase_total_krw,0) AS purchase_total_krw, COALESCE(pur.unpaid_krw,0) AS unpaid_krw,
       COALESCE(pur.settled_kg,0) AS settled_kg, pur.last_delivered_on, pur.last_paid_on, COALESCE(pur.purchases_since_pickup,0) AS purchases_since_pickup
FROM purchase_inquiry i
LEFT JOIN partner p ON p.id = i.partner_id
LEFT JOIN qc  ON qc.inquiry_id = i.id
LEFT JOIN lq  ON lq.inquiry_id = i.id
LEFT JOIN qp  ON qp.purchase_quote_id = lq.latest_quote_id
LEFT JOIN pur ON pur.inquiry_id = i.id
WHERE i.deleted_at IS NULL;
NOTIFY pgrst, 'reload schema';
```

## 13. 리스크·가정

- **업무 흐름 전체가 [추측]** — 고철·계근·공제·수거 실데이터 0건. 특히 '계근 = 당사 상차·공인 계근대·당일 송금'(`PURCHASE_QUOTE_DEFAULT_TERMS` [확인 `lib/purchase-quote.ts:28-32`]) 이 실제와 다르면 결제 순서가 바뀐다. 그래서 PR-0 통화 + PR-1 만 먼저. 흐름이 "전화 → 바로 트럭 → 계근 → 송금" 으로 짧아도 파생이 깨지지 않는다 — **매입 등록은 어느 열린 단계에서나 ▾ 로 가능하고 수거 확정은 선택**(§4.1), RPC 가 `pickup_on` 을 채운다.
- **`create_purchase_with_lines` 재정의**가 운영 `createPurchase`(수동 매입 폼)를 지난다. 새 키는 전부 NULLIF/COALESCE 옵션이지만 레포에 자동 회귀 테스트가 없다 — **재정의(0098)·호출측·전후 payload 비교 SQL 1개를 PR-3 한 PR 에** 넣고 PR-1(0097)에는 매입 측 변경을 두지 않는다. `createPurchase` 반환값 `{ok,id}` 변경은 호출처(폼) 1곳.
- **종결 RPC ↔ 8-a 동시성** — 종결 RPC 가 문의 행을 `FOR UPDATE`, 8-a 가 `FOR SHARE` 로 잡아 COUNT~UPDATE 사이 매입 INSERT 를 직렬화(1인 운영이라 확률은 낮다).
- **`PurchaseFormDialog`(628줄 [확인]) 수술** — `defaults`·계근/공제·결제예정일 칩·hidden 필드·거래처 등록 버튼. 비 prefill 경로의 `actualWeight = qty` 규약과 접힘 기본값으로 기존 사용성을 바꾸지 않는다. PR-3 1.5일은 낙관일 수 있음.
- **백필 건수 미확인** — 0075 배포(2026-10-14) 이후 생성분이라 소수로 가정 [추측]. PR-1 전 운영 DB `SELECT COUNT(*) FROM purchase_quote` 1회. 백필 DO 블록은 audit 트리거 전에 돌려 actor 'system' audit 를 남기지 않는다.
- **partner INSERT 는 owner/manager 전용**(`0019:266-293` [확인]) — staff 가 `[이 이름으로 거래처 등록]` 을 누르면 실패. **site INSERT 도 같은 정책**(`0031:55-56` [확인]) — staff 가 새 현장명으로 등록하면 `site_name` 텍스트만 남고 마스터는 안 생긴다. 사장 1인 운영이면 실무 문제 없음. 안내 문구로 명시.
- **`findExistingPartner` 전화번호 매칭** — `partner.phone` 저장 형식이 혼재할 수 있어 `phoneMatches`(`lib/radar/nara-rules.ts:42`, `radar-data.ts:9` 에서 import) 류 끝 4자리 + digitsOnly 비교로. 동명 거래처 여럿이면 가장 먼저 만든 것(기존 관례).
- **문자 실효 가드** — 레이더 밖 번호는 `recipientPhoneConsent` 가 즉시 통과(`:839` [확인]) 하므로 실효 가드는 거래처 거절 기록 + 사장 confirm 뿐. 법률 확인 전 [추측].
- **`revalidateTransactionPaths`** 에 보드 경로를 넣지 않으면 결제·등록 뒤 보드가 stale(`lib/transaction.ts:24-32` [확인]) — PR-3 포함.
- **뷰 성능** — 문의 수백·매입 수백 규모에서 집계 5개 CTE 는 문제없음 [추측]. 완료 90일 컷. 수만 행이 되면 인덱스 3개가 받친다.
- **`vw_inventory` 에 고철 lot 노출** — 재고 화면이 category 로 구분하는지 미확인(`inventory/page.tsx:54` select 에 category 있음 [확인]). PR-3 에서 '고철' 필터 칩 1개 필요 시 추가.
- **b 책 사진 버튼 숨김**의 부작용 — b 책 문의는 사진 없이 단가를 정해야 한다. 사장이 불편하면 §12-7 대안(private 버킷)으로.
- **견적 상세 '매입 완료' 버튼 제거** — 운영자가 익숙해졌을 수 있다. [보드로] + 안내.
- **`chk_pl_weigh_consistency`** — 기존 행은 NULL 통과. 확정 계산은 RPC(앱 부동소수 값을 덮어씀)라 등록 경로에서는 걸리지 않는다. `updatePurchaseHeader`(`purchases/actions.ts:220-262`) 는 라인을 안 건드려 지금은 안전하지만 향후 라인 수정 경로가 생기면 `actual` 만 바꿔도 걸린다 → 수정 폼은 gross/deduct 를 같이 받거나 둘을 NULL 로 리셋. `friendly()` 매핑은 §9.
- **UTC today** — `purchases/actions.ts:267,299,356` 의 날짜 오차가 보드 '오늘' 과 어긋난다 → PR-3 `kstToday` 통일. **DB 함수도 포함**: 새 DDL 의 기본값·RPC 는 `kst_today()`(§5.1 (0)), `CURRENT_DATE` 는 쓰지 않는다. `vw_payable`·뷰 `overdue_count` 의 `CURRENT_DATE` 는 기존 기준 그대로(00~09시 KST 에 하루 늦게 연체 판정 — 기존 동작).
- **백필 전제** — 판매자·현장 모두 NULL 인 견적이 있으면 `chk_pi_seller_or_site` 로 0097 전체가 롤백된다 → seller_name 폴백 + NOTICE(§5.1 (10)). 백필 UPDATE 가 기존 견적 `updated_at` 을 갱신한다(감수).
- **매입 연체 cron** — `notify-overdue.ts:47` 의 `.neq("status","cancelled")` 가 enum 에 없는 값이라 매입 연체가 조용히 0건일 가능성 [추측] → PR-4 에서 제거 + 실측.
- **attachment CHECK 교체** — 기존 6종(0077 `purchase_quote` 포함) 유지 + 1종 = 7종, DROP/ADD 한 트랜잭션. `purchase_quote` 를 빠뜨리면 기존 명함 행 때문에 ADD CONSTRAINT 가 실패한다.
- **`chk_pi_closed_reason`·RPC 순서** — 종결 RPC 가 `closed_at`·`close_reason` 을 한 UPDATE 로 바꾸므로 CHECK 위반 없음. 앱이 `closed_at` 을 직접 UPDATE 하면 CHECK 가 막는다(의도).
